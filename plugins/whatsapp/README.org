#+title: plugins/whatsapp — WhatsApp bridge for slave-agent

- Stage: CHARTER — contract only; no code exists anywhere yet

* What it will give the agent

A WhatsApp bridge, mirroring the user's WhatsApp account through the
platform's supported API surface:

| Tool (working name) | Returns / does                                |
|---------------------+-----------------------------------------------|
| ~wa_chats~          | recent chats/conversations (read-only)         |
| ~wa_messages~       | messages of one chat (read-only)               |
| ~wa_send~           | send a message — *gated*, see below            |

plus ~hermes wa~ (subcommand) and ~/wa~ (slash command).

* Configuration (profile config.yaml)

#+begin_src yaml
  plugins:
    entries:
      whatsapp:
        settings:
          # transport settings (endpoint/session), shape defined when
          # the implementation picks its supported API surface
          ...
#+end_src

Credentials ride the profile's secret scope and are read through
~agent.secret_scope~ at *call time* — env var NAMES only, never in
chat, files, commits or logs.

* Structural rules

1. *Read-only first.* ~wa_chats~ / ~wa_messages~ land before any send
   path. ~wa_send~ exists only behind the approve-before-send gate
   (Owner confirmation per outbound message); until the gate exists in
   the core, this plugin ships no send tool at all.
2. *No account automation tricks.* The bridge uses a supported API
   surface; no scraping, no ToS-violating automation.
3. *PII discipline.* Message bodies passing through the model are
   redacted at the prompt boundary once the core's PII redactor lands
   (slave-agent roadmap); until then the README states the exposure
   honestly.

* Tests

~tests/~ with the implementation; gate is the core's
~scripts/run_tests.sh tests/plugins/test_whatsapp_plugin.py~ (never
bare pytest — CI parity).
